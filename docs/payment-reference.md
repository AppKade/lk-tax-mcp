## Periods and deadlines

The September notice explicitly identifies Individual Income Tax as tax type **05**. Return-guide page 4, section 8 supplies the five YA 2025/26 payment codes. Calendar pages 4-5 separately confirm the final payment and the first two YA 2026/27 codes. Circular page 1 supplies the four YA 2026/27 nominal dates and says payment instructions will be supplied separately.

No code is generated by concatenation or inferred from neighbouring quarters. An unsupported year, final period or return period fails lookup. The November 2026 **return** deadline and its four-digit period `2526` must not replace the September **payment** deadline/code. The calendar's August SET entry is not used to override the later re-revised circular's declaration/attachment requirements. No weekend or public-holiday extension is inferred.

## Channels and remaining field mapping

The September notice points to the official OTPP information page. It also directs in-person payers to any BOC branch, obtaining a DIN through the IRD paying-in-slip service or the notice's telephone service, and entering that DIN in the payment-voucher-number field. It warns that interest and penalties apply after the deadline. That warning does not establish whether a particular user owes tax, an overdue balance, a penalty amount or interest.

The linked OTPP guide describes the bank's IRD payee flow, entry of TIN, taxable period/calendar year, tax type and payment type, then IRD validation and voucher selection. Its example screens use historical corporate/VAT data. A five-digit payment period code is not automatically the value to type into every bank's taxable-period field. Current IIT field mapping, voucher behaviour and bank-specific screens remain untested. The guide's notes on page 7 make payment/settlement timing subject to bank rules. No bank credentials, TIN, account details or DIN belong in this catalogue or its tests. No banking or IRD payment session was opened.

## Checks and activation gates

Run `npm run payments:check`. It validates strict catalogue shape, source/citation links, distinct records, code-versus-evidence consistency and agreement with existing planner dates. It emits a development report with `actionable: false`, `filing_ready: false`, `payment_amount: null` and explicit blockers. Completing a metadata check cannot activate payments.

For optional byte verification, download the five public PDFs under the manifest's local filenames and run:

```sh
npm run payments:check -- --source-dir /absolute/path/to/downloads
```

This checks complete bytes against recorded size and SHA-256 without network calls or executing source content. Ordinary CI sets `source_bytes_checked: false`; the capture check for this milestone used all five complete PDFs and returned true.

Before runtime integration, obtain supported-year rounding authority and qualified review, complete current bank-field/flow verification and recheck applicable notices. Rounding remains unresolved: the current annual guide and linked OTPP guide yielded no explicit policy. Search found a nearest-rupee instruction in the [2017/18 individual guide](https://www.ird.gov.lk/en/Downloads/IT_Individuals_Doc/IIT_IR14_2017_2018_E.pdf); that historical instruction is not applied to YA 2025/26 or 2026/27. No amount, late-payment charge or payment confirmation is produced by this work. Any future runtime integration must follow rule governance, consent/scope/checklist controls and public-contract versioning.
